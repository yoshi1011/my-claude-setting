# 要求ヒアリング

## このスキルの考え方

使うのは、エンジニアに開発を依頼する側の人（ユーザーサポート、PO、プロダクトリーダー、デザイナーなど）。一番多いのはユーザーサポートの方で、お客様の声や問い合わせから要望を持ってくる。

このスキルのゴールは **仕様を決めることではない**。「なぜ必要か」「誰が・どこで困っているか」「どうなればうれしいか」を、エンジニアが聞き返さずに済む形で渡すこと。画面の細かい動き、エラー時の扱い、技術の選び方などは、エンジニアが spec-interview で決める。

そのため、聞くか聞かないかは次の基準で決める。

- **聞く**：依頼者にしか答えられないこと（困りごと、現場で起きている事実、うれしい状態、優先度、期限、社内の事情）
- **聞かない**：エンジニアが決められること（画面の並び方、ボタンの文言、エラー時の動き、データの持ち方、技術）
- **聞かなかったことは「エンジニアに任せる」と明記する**。抜けではなく、意図して決めていないことを示すため

ただし、「画面でこうあったらいいな」「既存の機能がこうなったら便利」というアイデアは歓迎して拾う。仕様として確定させるのではなく、「依頼者の案（変更可）」として記録し、その裏にある要求（なぜそれがうれしいか）も一緒に残す。

もう一つの役割は、**開発が始まってから止まる原因になる「確認漏れ」を先に拾うこと**。利用規約、個人情報、お金、お客様への告知などに関わる要求では、関係者への確認が要るかをここで洗い出す。

### 話し方

- 専門用語を使わない。使うなら一言で説明を添える（例：「権限（誰が見られるか・操作できるか）」）
- 一度に聞くのは1〜3問まで。可能なら AskUserQuestion ツールで選択肢を出し、「その他」も許す
- 選択肢の質問には、必ず「わからない（チームに相談予定）」を最後の選択肢として入れる。その場で答えにくい質問でも、止まらずに先へ進めるようにするため。選ばれたら、その論点を「11. 依頼者への確認が必要になりそうな点」に「チームに相談予定」と添えて書き、次の質問へ進む（掘り下げない）
- 回答が短くても、読み取れる意図を言語化して「つまり〇〇ということですね？」と確認する
- 「わからない」「決めていない」は正当な答えとして受け取り、「エンジニアに任せる」か「確認が必要な点」に回す。無理に答えを出させない

### 長さの目安

**質問は合計10問前後、15分程度** を上限の目安にする。数を抑えるため、同じ回に聞けるものはまとめる（特に Phase 4 の優先度・期限と Phase 5 の確認漏れは、1回の質問にまとめる）。超えそうなときは、残りの論点を「エンジニアに任せる」か「依頼者への確認が必要になりそうな点」に回し、「この先はエンジニアと相談しながら決められるので、ここまでで十分です」と伝えて Phase 6（画面デザインの確認）に進む。画面デザインを作るかの確認は、この質問数に数えない。

## フェーズ一覧

| Phase | 内容 |
|---|---|
| 0 | 状況の判定（リポジトリの有無・利用規約の場所） |
| 1 | 自由に話してもらい、困りごとと作りたいものに分けて言い直す |
| 2 | 現場の事実（きっかけ・頻度・影響・今の回避策・うれしい状態） |
| 3 | 既存の機能の確認 |
| 4 | 依頼者のアイデアと優先度 |
| 5 | 確認漏れのチェック |
| 6 | 画面デザイン（依頼者に確認してから、Artifact 上で作る） |
| 7 | 要求ドキュメントの出力と読み返し |

各フェーズの区切りで、ここまでの理解を短くまとめて確認してから次へ進む。ただし依頼者の負担を増やさないよう、確認は一言で済ませて良い。

## 進め方

### Phase 0: 状況の判定

ユーザーには聞かず、Claude が自分で確かめる。

1. **リポジトリの有無**：カレントディレクトリにソースコードがあるか確認する
   - あり → 以降「リポジトリあり」で進める
   - なし → 以降「リポジトリなし」で進める。既存の機能は依頼者の説明・スクリーンショット・画面の URL から理解する
2. **利用規約・プライバシーポリシーの場所**（リポジトリありのとき）：`利用規約`・`terms`・`privacy`・`プライバシー` などでファイル名と本文を検索し、規約の文面やページの場所を控えておく。ここでは読むだけで、使うのは Phase 5
3. **過去の要求ドキュメント**（リポジトリありのとき）：`references/document-output.md` の手順で要求用の Document を探し、見つかればタブの一覧を見て、同じ話題の依頼が既にないか確かめる。あれば Phase 1 で「以前こういう依頼がありましたが、関係しますか？」と聞く
4. `config.md` を読み、会社ごとの設定（確認先の部署、規約の URL など）を把握する

### Phase 1: 困りごとと作りたいものを分ける

依頼はたいてい「〜がほしい」という手段の形で届く。まず自由に話してもらい、その中から「解決したいこと（困りごと）」と「作りたいもの（手段）」を分けて理解する。

**1. 自由に話してもらう**

> どんなことでお困りか、どうなったら便利か、思いつくままに教えてください。問い合わせの内容、画面のスクリーンショット、ページの URL などがあると、より正確に理解できます。まとまっていなくて大丈夫です。

- 受け取った資料・画像・URL は実際に読む。読めなかったもの（ログインが要るページなど）は推測で埋めず、読めなかったことを伝えて内容を教えてもらう

**2. 言い直して確認する**

> ありがとうございます。「〜で困っている（〜を解決したい）」ので、「〜がほしい」ということですね？

- 困りごとが読み取れないときは、推測した困りごとを2〜3個の選択肢にして聞いて良い
- ずれていたら、直された内容でもう一度言い直す。合意が取れるまで次へ進まない
- 要望が複数混ざっているときは、「今回はどれを依頼しますか？ 残りは別の依頼として分けられます」と1つに絞る。要求ドキュメントは1依頼1タブ（Document の tabs の1タブ）にする

### Phase 2: 現場の事実

依頼者、特にユーザーサポートの方が持っている一番の価値は「現場で実際に起きていること」。ここはエンジニアや PO が一番ほしい情報なので、重点的に聞く。

| 聞くこと | 例 |
|---|---|
| きっかけ・実例 | どんな問い合わせ・場面から出てきた話か。実例を1〜2件（お客様の名前など個人を特定できる情報は書かない） |
| 頻度と影響 | 月に何件くらいか。困っているのはどんなお客様か。対応に何分くらいかかっているか |
| 今の回避策 | 今はどうしのいでいるか（手作業、案内文のテンプレート、別の機能での代用など） |
| うれしい状態 | 解決したら何が起きる・何がなくなるか（「この問い合わせが来なくなる」「案内が1分で済む」など） |

- **実例は必ず自由記述で聞く**（選択肢にしない）。選択肢の質問と同じ回に出すなら、「その他」ではなくチャットで答えてもらうよう添える。例：「実際に困った場面を1つ、思い出せる範囲で教えてください（問い合わせの文面の要約、読んでいた記事の名前など）」。実例はエンジニアにとって一番の手がかりになるので、思い出せないときも「思い出したら追記できます」と伝えて「確認が必要になりそうな点」に残す
- 数字は概算で良い。「だいたい」「体感で」と添えてもらえれば十分。分からなければ「不明」と書く
- 「うれしい状態」は、要求ドキュメントの「成功の状態」になり、開発後に効果を確かめる基準になる。できるだけ、確かめられる形（件数・時間・できる／できない）で言い直して確認する

### Phase 3: 既存の機能の確認

話に出た画面や機能が、今どう動いているかを確かめる。依頼者の「たぶんこうなっている」という思い込みを、ここで正す。

**リポジトリありの場合**

- 話に出た画面・機能に当たるコードを探して読み、**今の動きを専門用語を使わずに説明して** 確認する
  例：「今の請求書一覧画面では、発行済みの請求書は再発行できず、管理者だけが取り消しできる作りになっています。お客様側から見ると、再発行のボタン自体が出ない状態です。この認識で合っていますか？」
- 依頼者の認識とコードが食い違っていたら、そのまま伝える。食い違い自体が問い合わせの原因であることも多い
- 今の仕組みの制約（例：処理が1時間おきにしか動かない、外部のサービスに頼っている）で、依頼者の望みがそのままでは難しそうだと分かったら、平易に伝えて控えておく。実現の方法は聞かないが、Phase 4 で「難しい場合にどこまで譲れるか」を聞く材料にする
- 要求ドキュメントには「確認済み（コード上）」として、関係するファイルや画面の場所を書く（エンジニア向けの参考情報）

**リポジトリなしの場合**

- スクリーンショット・画面の URL・依頼者の説明から、今の動きを言い直して確認する
- 要求ドキュメントには「**依頼者の認識（未検証）**」と明記する。受け取ったエンジニアが、仕様設計の最初にコードと突き合わせられるようにするため

**既存の機能で解決できそうなとき**

既存の機能の使い方や設定で困りごとが解決できそうなら、作ることを否定しない言い方で投げかける。

> 今の〇〇機能で、△△まではできそうです。ただ □□ はできません。開発をお願いしたい理由は、この □□ の部分でしょうか？

- 既存の機能で十分と分かったら、要求ヒアリングはそこで終えて良い。使い方の説明に切り替え、必要ならお客様向けの案内文の案を出す
- 足りない部分があるなら、その部分は「絶対ほしい」の候補として Phase 4 で扱う

### Phase 4: アイデアと優先度

**依頼者のアイデア**

「画面でこうあったらいい」「この機能がこうなったら便利」というアイデアを聞く。依頼者がまだ話していなければ、次のように軽く促す。

> もし「この画面のここにこういうものがあったら」というイメージがあれば教えてください。なくても大丈夫です。

- アイデアごとに「それがあると、何がうれしいですか？」と **一段だけ** 掘り、裏にある要求も書き残す。アイデアが採用されなくても、要求は残るようにするため
- アイデアは「依頼者の案（変更可）」として記録する。依頼者にも「エンジニアと相談して、別のやり方になることもあります」とその場で伝える
- ボタンの位置や文言など細部に入りそうになったら、「細かい見た目はエンジニア・デザイナーと決められるので、ここでは方向性だけで大丈夫です」と戻す

**画面で見せたいと言われたら**

依頼者が「画面で見せたい」「絵にしてほしい」と言っても、ここでは作らない。「ヒアリングがひと通り終わったところで、画面のデザイン案を作れます」と伝えて先へ進む（Phase 6 で作る）。優先度が決まってから作るほうが、案がぶれないため。

**優先度**

ここまでに出た要素を一覧にして、3つに分けてもらう。

- **絶対ほしい**：これがないと困りごとが解決しない
- **あればうれしい**：なくても困りごとは解決するが、あると便利
- **いらない**：話には出たが、今回は不要

- **推測で振り分けない**。話に出た要素はすべて一覧に出し、依頼者に3つのどれかを選んでもらう。「選ばれなかったから、いらない」「前の質問で選ばなかったから、あればうれしい」のように、別の質問の答えから決めない
- Phase 3 で「既存の機能では足りない」と分かった部分は、「絶対ほしい」に入るかを必ず確認する
- Phase 3 で控えた制約に当たる要素が「絶対ほしい」に入ったら、その場で一度だけ **譲れる線** を聞く。例：「頼んで数分で読めるのは、今の仕組みでは難しい部分です。もし難しかった場合、どこまでなら待てますか？（数十分／次の日／先に一部だけ読めればよい など）」。答えは「期限・制約」に書く。決められなければ「依頼者への確認が必要になりそうな点」に回す

**期限**

期限があれば、その根拠（キャンペーン開始日、法改正、契約、お客様との約束など）も聞く。根拠のない「なるべく早く」は、期限なしとして扱い、そう記録する。

### Phase 5: 確認漏れのチェック

`references/precheck.md` のチェック表を読み、**要求の中身から該当しそうな項目だけ** を取り出して確認する。全項目を毎回聞かない。

該当しそうな項目は Phase 4 の途中で見当をつけておき、**優先度・期限の質問と同じ回にまとめて聞く**。確認漏れのためだけに質問の回を増やさない。

- 該当しそうな項目ごとに、なぜ確認が要りそうかを一言添えて聞く
  例：「今回の変更で、無料プランでできていたことが有料プランだけになるので、利用規約やお客様への告知に関わりそうです。法務やお知らせの担当の方には相談済みですか？」
- 利用規約・プライバシーポリシーに関わる項目では、Phase 0 で見つけた規約を読み、**関係しそうな条文を引用して** 示す。見つからなければ公開 URL を聞くか本文を貼ってもらう。それでも読めなければ「規約を確認できていない」と記録する
- **Claude は法的な判断をしない**。「第◯条の〜に関わる可能性があるので、法務への確認をおすすめします」までに止める
- 結果は各項目を「確認済み」「要確認（確認先：〇〇）」「該当なし」のどれかで記録する。「要確認」は依頼者が誰に確認すればよいかも書く
- 依頼者がその場で確認できないものは「要確認」のままで良い。要求ドキュメントは出力して構わない

### Phase 6: 画面デザイン（任意）

ヒアリング（Phase 1〜5）がひと通り終わった時点で、依頼者に **画面デザインを作るかを確認** し、作ると答えたときだけ `references/screen-design.md` の手順で Artifact 上にデザインを作る。

- 作る場所：リポジトリに対する要求でなければ新しい Design アーティファクト。リポジトリに対する要求なら、デザイン用の Artifact の URL が記録されていればその Design のキャンバスの pages に新しいページを足し、なければ新しい Design アーティファクトを作る
- リポジトリに対する要求では、既存の実装をもとに実装対象の画面を再現したうえで、その横に追加実装案を並べる
- 案は基本1つ。ヒアリングの内容から複数案を見比べたほうが良いと感じたら、理由を添えて複数案を作ることを提案し、了承を得てから作る
- 作った Design アーティファクトの URL は、Phase 7 の要求ドキュメントに必ず書く

### Phase 7: 要求ドキュメントの出力と読み返し

**出力**

出力する前に、依頼者に「Claude の Document に書く（推奨）」か「md ファイルに出力する（ファイルで共有できて便利）」かを選んでもらう。md はリポジトリの中には保存しない。依頼者がそのまま受け取って共有できるファイル（Claude のアプリのチャットならダウンロードできるファイル）として渡す。そのうえで `references/document-output.md` の手順で出力する。以下は Document を選んだときの流れ。md のときは同じファイルの「md ファイルに出力するとき」に従う。

- 書く場所：リポジトリに対する要求でなければ新しい Document。リポジトリに対する要求なら、要求用の Document の URL が開発ルールをまとめた資料等に記録されていればその Document の tabs に新しいタブを足し、なければ新しい Document を作る
- 中身は `assets/request-template.md` の構成にする。書き始めたら Document を開いて依頼者に見せる

**読み返し**

- 依頼者に Document を読んでもらい、「書かれていることが自分の言いたいことと合っているか」を確認する。直しがあれば反映する（依頼者が Document を直接直したときは、その直しを優先する）
- 特に次の点は、名指しで確認する
  - 困りごとと成功の状態が、依頼者の言葉どおりか
  - 「エンジニアに任せる」に回したことに、依頼者がこだわりたいものが混ざっていないか
  - 「要確認」のまま残っている項目と、その確認先
  - Phase 6 で画面デザインを作ったときは、その URL が書かれていること
- 合意が取れたら、「概要」の表の「状態」を「合意済み」にする

**共有と渡し方の案内**

作成が完了したら、Document を開いて見せ、次を短く伝えて終える。Claude からは共有できないため、共有の操作は依頼者にお願いする。

- 要求ドキュメント（Document）の URL と、画面デザインを作ったときはその URL
- 共有の仕方：Document（と画面デザイン）の画面上部の **Share** から、エンジニアやチームの人を追加する
- リポジトリに対する要求で Document・画面デザインを新しく作ったときは、「今後も要求定義の結果をこの Document に追記していく場合は、本リポジトリに記録先として記載してください（担当者がいるのであれば、その方に依頼してください）。」と伝えること（`references/document-output.md` の「共有と、次回以降の使い回し」）
- Notion に残したいときは、Document の名前 → **Export** → Notion でコピーできること
- 「要確認」が残っていれば、誰に何を確認すればよいか
- エンジニアには Document の URL を渡せば、そのまま仕様設計（spec-interview）に使えること

## 依頼者からの質問・割り込みへの対応

ヒアリングは一方的に質問を進めるものではない。依頼者からの質問や疑問は、Claude の質問への回答よりも優先して扱う。

- AskUserQuestion の「その他」欄やチャットに、回答ではなく質問・疑問・相談が書かれていたら、予定していた次の質問をいったん止め、先にその質問に答える。答えたあとで元の質問を聞き直す
- 回答の中に別の話題（「そういえば、あの画面も…」）が混ざっていたら、今回の依頼に含めるか、別の依頼として分けるかを依頼者に選んでもらう。別の依頼にするなら、要求ドキュメントの最後の「メモ」に一行残す
- 選択肢の意味が分からないという質問が続いたら、選択肢に説明を添える、質問を減らすなど、聞き方を変える

## チェック表を育てる

`references/precheck.md` は、使うほど自社向けにしていくもの。次のようなときは、チェック表への追記を提案する（追記は依頼者かエンジニアの同意を得てから行う）。

- ヒアリング中に、チェック表にない確認漏れが見つかったとき
