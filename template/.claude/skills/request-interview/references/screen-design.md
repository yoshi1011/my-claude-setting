# 画面デザイン（Phase 6）

ヒアリング（Phase 1〜5）がひと通り終わり、困りごと・成功の状態・依頼者のアイデア・優先度が出そろった時点で、**依頼者に確認したうえで** 画面デザインを作る。

目的は **要求を画面の形で伝えること**。見た目を完成させることではない。依頼者が細部（余白・文言・色）を詰め始めたら、「細かいところはエンジニア・デザイナーと決めるので、ここでは方向性が伝われば十分です」と戻す。

## 1. 作るかどうかを確認する

AskUserQuestion で、次のように聞く。こちらから毎回聞いて良いが、作るかどうかは依頼者が決める。

> ここまでの内容をもとに、画面のデザイン案を作りましょうか？ 画面の形で見られると、エンジニアにもイメージが伝わりやすくなります（5〜10分ほどかかります）。

- 選択肢：「作る」「作らない」「わからない（チームに相談予定）」
- ヒアリングの内容から複数のデザイン案があると良いと判断したときは、「作る」を「作る（1案）」と「作る（複数案）」に分け、複数案の選択肢の説明に **なぜ複数案が良さそうか** を一言添える（「3. デザインの中身」の「複数案の提案」）。複数案のほうが良いと考えるなら、そちらを先頭にして（おすすめ）を付ける
- 「作らない」「わからない」なら、そのまま Phase 7 へ進む。要求ドキュメントの画面デザインは「なし」にする
- 画面に関係しない依頼（集計・通知の裏側の処理、データの直しなど）では聞かずに Phase 7 へ進む
- Artifact ツールが使えない環境では聞かずに Phase 7 へ進み、「この環境では画面デザインを作れないため、必要なら Claude のアプリで作れます」と一言添える

## 2. デザインを作る場所を決める

ユーザーには聞かず、Claude が判定する。

| 状況 | 作る場所 |
|---|---|
| リポジトリなし（何らかのリポジトリに対する要求ではない） | 新しい Design アーティファクトを作る |
| リポジトリあり・デザイン用の Artifact の URL が記録されている | **その Design のキャンバスの pages に新しいページを足す** |
| リポジトリあり・デザイン用の Artifact の URL が記録されていない | 新しい Design アーティファクトを作る |

**デザイン用の Artifact の URL の探し方**（リポジトリありのとき）

`docs/design.md` その他開発ルールをまとめた資料等に記録されていないかを確かめる。記録の場所はリポジトリによって違うため、特定のファイルに決め打ちしない。

- `docs/design.md`（request-interview・spec-interview で作ったデザインのリンクを記録する場所）
- 開発ルールをまとめた資料（例：`CLAUDE.md`、`README.md`、`CONTRIBUTING.md`、`docs/` 配下の開発ルール・デザインの資料、`docs/spec.md` の「Claude Design：」の行）
- 上で見つからなければ、リポジトリ内を `claude.ai/artifact/`・`claude.ai/code/artifact/` で検索し、デザイン用と書かれているもの
- デザイン用らしい URL が複数あって決められないときは、依頼者に「どちらに追加しますか？」と選んでもらう

見つかった URL が旧サービス（`claude.ai/design`）のものしかない場合は使わず、新しい Design アーティファクトを作る（旧サービスは 2026年12月14日に終了するため）。

**新しい Design アーティファクトを作るとき**

- Artifact ツールの quickstart（intent: design）から始め、返ってきた手順に従う
- タイトルは `要求：<短い名前>`（Phase 7 の要求ドキュメントと同じ短い名前）にする
- Design System（会社のデザインの部品集）が登録されていれば、それを使う

**既存のデザイン用 Artifact のキャンバスの pages に新しいページを足すとき**

1. Artifact ツールの `action: "read"` でその Artifact を読み、返ってきた type の手順に従う
2. 結果に編集できる（`writer`）と出ていることを確かめる。編集できない・Design の形式ではないときは、新しい Design アーティファクトを作り、「既存のデザインは編集できなかったため、別に作りました」と依頼者に伝える
3. キャンバスの pages（キャンバスの中のページの一覧）に、新しいページを `要求：<短い名前>（YYYY-MM-DD）` という名前で足す。既存のページの中に画面を描き足すのではなく、ページそのものを1つ増やす。**既存のページは書き換えない**
4. 既存のページにある部品・配色・Design System を、新しいページでもそのまま使う

## 3. デザインの中身

### 案の数と、複数案の提案

基本は **1案**（依頼者のアイデアがあれば、それを反映した案）を作る。ヒアリングの内容から、次のように複数案を見比べたほうが判断しやすいと感じたときは、複数案（2〜3案）を作ることを依頼者に提案し、了承を得てから作る。黙って案を増やさない。

- 依頼者が方向性に迷っている、または話の中で考えが揺れていた
- 手軽さと機能の多さなど、両立しにくいものを天びんにかけている（例：「すぐ使える」と「細かく設定できる」）
- 「あればうれしい」を入れるかどうかで、画面の形が大きく変わる
- 依頼者のアイデアとは別のやり方のほうが、困りごとをうまく解決できそう、または既存の部品をより活かせそう
- 機能を置く場所（今の画面に足す／別の画面にする など）の候補が複数ある

提案するときは、どの点で案が分かれるかを一言で示す（例：「再発行の入り口を一覧に置く案と、詳細画面に置く案で見比べると決めやすそうです」）。複数案にしたら、各案の名前（`依頼者の案`・`追加案A`・`追加案B` など）と、案ごとの狙い・違いを注記に書く。

### リポジトリありの場合：既存の実装を再現してから、追加実装案を考える

1. **実装対象の画面を再現する**
   - Phase 3 で確かめた画面のコードを読み、画面の構成（ヘッダー・検索欄・表など）、配色やフォント、余白、ボタンの形を写す。配色などは、デザインの値をまとめたファイル（色・余白・角丸の定義）があればそこから取る
   - 既存のデザイン用 Artifact に同じ画面があっても、**正はコード**。デザインと実装が食い違っていたら実装に合わせ、食い違いがあったことを依頼者に伝える
   - ロゴなどの画像がリポジトリにあれば、アップロードして使う
   - 実データやログインの状態で変わる部分は、コードから想定して描く
   - 再現した画面には「今」と分かる名前を付ける（例：`請求書一覧（今）`）
2. **追加実装案を考える**
   - 再現した画面を複製し、要求を満たす追加実装案を反映した画面を横に並べる。「今」と「案」を見比べられるようにする
   - 案は、要求ドキュメントの「絶対ほしい」を必ず満たすようにする。「あればうれしい」は、入れた案と入れない案で分けても良い
   - 依頼者のアイデアがあれば、それを反映した案（`依頼者の案`）を作る。なければ Claude が考えた案を1つ作る
   - 複数案の提案（上記）が了承されたときは、Claude が考えた別の案（`追加案A`・`追加案B`）を並べる
   - 既存のコンポーネント（ボタン・表・モーダルなどの部品）を使い回す前提で考える。新しく作る部品が要る案は、その部品が新規であることを画面の注記に書く
   - 各案の横に、「どの困りごと・成功の状態に効くか」「依頼者のアイデアとの違い」を短い注記で添える
3. 状態の違い（0件のとき・読み込み中・エラー時など）が話に関係するなら、切り替えて見られるようにしておく

### リポジトリなしの場合

- 既存の画面に手を加える案なら、依頼者のスクリーンショットや画面の URL から近い画面を再現し、その横に案を並べる。再現の精度は落ちることを伝える
- まったく新しい画面なら、要求（困りごと・成功の状態・優先度・アイデア）から画面を作る。複数案にするかは「案の数と、複数案の提案」に従う

## 4. 依頼者に見てもらう

- 作った画面を開いて見てもらい、「困りごとが解決しそうか」「アイデアの意図が伝わっているか」を確認する。直しは方向性に関わるものだけ反映する
- 選ばれた案・気に入った点があれば、要求ドキュメントの「6. 依頼者のアイデア」に追記する（依頼者の案として、変更可のまま）

## 5. URL を要求ドキュメントに載せる

作った（またはキャンバスの pages にページを足した）Design アーティファクトの URL を、Phase 7 で書く要求ドキュメント（Document）に **必ず** 書く。エンジニアが次のステップ（spec-interview）で、ここから仕様設計のデザインを始められるようにするため。

- 「概要」の表の「画面デザイン」と、「6. 依頼者のアイデア」の「画面デザイン」に URL を書く。既存の Design のキャンバスの pages にページを足したときは、足したページ名も書く
- 共有と次回以降の使い回しは、要求ドキュメントと同じ扱いにする（`references/document-output.md` の「共有と、次回以降の使い回し」）。Phase 7 の最後に、要求ドキュメントと一緒に共有の操作を案内する。新しく作ったときは「今後も要求定義の結果をこの Design に追記していく場合は、本リポジトリに記録先として記載してください（担当者がいるのであれば、その方に依頼してください）。」と伝える

## 注意すること

- 表に入れるデータは **ダミー** にする。実在のお客様や企業の名前・個人情報を入れない
- 想定で描いた部分（実データやログインの状態で変わる部分）があることを依頼者に伝え、画面の注記にも書く
- デザインは「依頼者の案・Claude の追加案（変更可）」であり、仕様ではない。画面の注記と要求ドキュメントの両方にそう書く
- `docs/design.md` などのリポジトリのデザインの記録は Claude から書き換えない。新しく作った Design を次回以降も使い回すかは、担当のエンジニアに確認してもらう（要求ドキュメントと同じ扱い）。正式なデザインへの反映は、エンジニアが spec-interview で行う
