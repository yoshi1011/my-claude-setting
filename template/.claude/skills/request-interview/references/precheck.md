# 確認漏れのチェック表

Phase 5 で使う。開発が始まってから「その確認をしていなかった」で止まる・やり直しになるものを、要求の段階で拾うための表。

**全項目を毎回聞かない**。各項目の「こういう要求なら」に当てはまるものだけを取り出して確認する。当てはまらない項目は、要求ドキュメントの事前確認欄にも載せなくて良い。

確認先の部署名は `config.md` の「確認先」に合わせる。

## チェック表

### C1. お客様にとって不利になる変更

- **こういう要求なら**：機能をなくす・制限を足す・有料にする・今までの使い方ができなくなる・表示や順番が変わってお客様が戸惑う
- **確認すること**：
  - 利用規約を読み、関係しそうな条文を引用して示す。規約の変更が要りそうか
  - 事前にお客様へ告知が要るか（いつ・どの方法で）
  - 既に契約・購入しているお客様の扱い（移行期間、据え置きなど）
- **確認先の例**：法務、PO、お知らせの担当

### C2. 個人情報の扱いが変わる

- **こういう要求なら**：新しくお客様の情報を集める・見られる人が増える・社外のサービスに渡す・保存する期間が変わる・書き出し（エクスポート）できるようにする
- **確認すること**：
  - プライバシーポリシーを読み、関係しそうな箇所を引用して示す。ポリシーの変更や同意の取り直しが要りそうか
  - 社内で見てよい人の範囲
- **確認先の例**：法務、セキュリティの担当

### C3. お金が絡む

- **こういう要求なら**：料金・請求・返金・割引・ポイント・支払い方法に関わる
- **確認すること**：
  - 経理の処理や請求書の書き方に影響しないか
  - 返金や差額の扱いのルールが決まっているか
- **確認先の例**：経理、PO

### C4. お客様の見え方・操作が変わる

- **こういう要求なら**：画面の見た目・操作の手順・通知・メールの内容が変わる
- **確認すること**：
  - ヘルプページ・FAQ・問い合わせの返信テンプレートの更新が要るか
  - 社内の操作マニュアル・営業資料の更新が要るか
  - 事前の告知が要るか（C1 と重なるときはまとめて聞く）
- **確認先の例**：ユーザーサポート（依頼者自身のことも多い）、営業、お知らせの担当

### C5. 過去のデータにも関係する

- **こういう要求なら**：今あるデータの見え方・計算・状態が変わる、過去の分にもさかのぼって適用したい
- **確認すること**：
  - 過去の分にも適用するか、これからの分だけか
  - 切り替えの日や移行期間を設けるか
- **確認先の例**：PO

### C6. 誰が見られるか・操作できるか

- **こういう要求なら**：管理者だけ・一部のお客様だけ・プランによって、など、使える人を分けたい
- **確認すること**：
  - 誰が見られて、誰が操作できるべきかの業務上のルール（システムの作りではなく、業務として）
- **確認先の例**：PO、管理者

### C7. 期限がある

- **こういう要求なら**：「◯日までに」と期限が付いている
- **確認すること**：
  - 期限の根拠（キャンペーン・法改正・契約・お客様との約束など）
  - 期限に間に合わない場合、一部だけ先に出すことができるか
- **確認先の例**：依頼者、PO

### C8. 社内の合意

- **こういう要求なら**：ユーザーサポートなど、優先順位を決める立場ではない人からの依頼で、影響が大きそうなとき
- **確認すること**：
  - PO やプロダクトリーダーに話が通っているか
- **確認先の例**：PO、プロダクトリーダー

## 規約を読むときのルール

- リポジトリありなら、Phase 0 で見つけた規約・ポリシーのファイルやページを読む
- 見つからなければ、`config.md` の規約の URL を見る。なければ依頼者に公開 URL を聞くか、本文を貼ってもらう
- それでも読めなければ、推測で判断せず「規約を確認できていない」として「要確認」に残す
- **法的な判断はしない**。「第◯条の『〜』に関わる可能性があるので、法務への確認をおすすめします」までに止める
