# 仕様ヒアリング（チェックリスト方式）

## このスキルの考え方

ユーザーは最初から全要件を言語化できているわけではない。だから Claude が「聞く・推測して提案する・抜けを拾う」を能動的に行い、会話のキャッチボールを通じて仕様を固めていく。

仕様は **項目（カテゴリ）ごとに分割したチェックリスト** で管理する。こうすると、ユーザーは「プロフィールの経歴欄が気になる」のように場所を指して指摘しやすくなり、Claude も「どこが決まっていて、どこがまだ触れられていないか」を常に把握できる。

ただし項目単位の確認だけでは、項目同士のつながりの抜けや、会話の流れに引っ張られた見落としに気づきにくい。そのため後半で、具体的な利用シナリオでの通し確認と、別視点のレビューを行う。

また、ユーザーの好みは Obsidian のプロフィールノートに蓄積し、毎回同じ質問を繰り返さずに済むようにする。浮いた分の会話は、本当に考えるべき論点の深掘りに使う。

仕様が合意されるまでコードは書かない。

## フェーズ一覧

| Phase | 内容 |
|---|---|
| 0 | 状況の判定とプロフィールの読み込み |
| 1 | 要求の理解・代替案の確認・目的とゴール |
| 2 | チェックリストの骨組み |
| 3 | 項目ごとのヒアリング・提案・完了条件 |
| 4 | 未言及項目の拾い上げ |
| 5 | デザイン案 |
| 6 | シナリオ・ウォークスルー |
| 7 | 仕様レビュー（spec-reviewer） |
| 8 | 仕様確定とプロフィール更新 |

各フェーズの終わりに必ずユーザーの合意を取ってから次へ進む。

## 仕様ファイル

すべての決定事項は `docs/spec.md` に記録する。初回は `assets/spec-template.md` を元に作成する。既に `docs/spec.md` があるときは新しく作らず、`references/additional-development.md` の書き方で追記する。

### チェックリストの書式

各項目にはIDを振り、ユーザーが番号で指摘できるようにする。確定した項目には「どうなっていれば完成か」を示す完了条件を付ける。

```markdown
## 2. ログ入力 [INPUT]
- [x] INPUT-1 入力タイミング：作業ごとに都度一行で記録
  - 完了条件：ページを開いた時点で入力欄にフォーカスがあり、Enterで時刻付きで保存される
- [~] INPUT-2 経過時間の自動計算：前のログからの経過時間を表示する方向で検討中（昼休みの扱いが未定）
- [ ] INPUT-3 タグ付けの有無 ※未言及
- [-] INPUT-4 音声入力：対象外（PCでの利用が主のため）
```

ステータス記号：
- `[x]` 確定：ユーザーが明確に合意したもの。完了条件を必ず添える
- `[~]` 検討中：方向性は出たが合意前のもの。迷っている点を併記する
- `[ ]` 未確定：まだ話していないもの。ユーザーが一度も触れていない場合は `※未言及` を付ける
- `[-]` 対象外：ユーザーが不要と判断したもの。理由を併記する

ファイル冒頭には進捗サマリを置き、更新のたびに数を更新する：

```markdown
> 進捗：確定 12 / 検討中 3 / 未確定 8 / 対象外 2
```

### チェックを入れるタイミング

ユーザーの発言で合意が取れた時点で、その場で `docs/spec.md` を更新し、返答の中で何を確定したかを短く伝える。

例：「INPUT-1（都度一行で記録）を確定にしました。完了条件は『開いたら入力欄にフォーカス、Enterで保存』としています。」

推測だけで `[x]` にしない。Claude の提案にユーザーが明確に同意して初めて確定とする。曖昧な返事（「いいかもね」程度）は `[~]` にして、後で確認する。

### 完了条件の書き方

完了条件は、実装後に「できている／できていない」を判定できる具体的な状態で書く。後でそのままテスト項目として使える粒度を目安にする。

- 良い例：「検索欄に入力すると、本文とタグの両方から部分一致で絞り込まれる」
- 悪い例：「検索しやすくする」

完了条件はClaudeが案を出し、ユーザーに確認してもらう。ユーザーに一から書かせない。

## 進め方

### Phase 0: 状況の判定とプロフィールの読み込み

**状況の判定**

1. 新規か追加実装か：カレントディレクトリにソースコードまたは `docs/spec.md` があるか確認する。どちらかがあれば追加実装とする。判断がつかなければユーザーに聞く
2. 追加実装の場合、Claude Design のデザインがあるか：`docs/spec.md` や `docs/design.md` にリンクの記録がないか確認し、見つからなければ「このプロダクトのデザインは Claude Design で作っていますか？あればリンクを教えてください」と聞く
3. 追加実装の場合は `references/additional-development.md` を読み、以降のフェーズでは各フェーズの「追加実装の場合」の指示に従う

判定結果を記録する：
- A：完全新規
- B：追加実装（Claude Design あり）
- C：追加実装（Claude Design なし）

新規なら `docs/spec.md` の冒頭の「前提」に書く。追加実装で既に `docs/spec.md` があるときは、冒頭の種別（最初の開発のときの判定）は書き換えず、今回の追加の節に書く（`references/additional-development.md` を参照）。

**プロフィールの読み込み**

`references/obsidian-profile.md` の手順に従い、Obsidian の Vault からユーザープロフィールを読み込む。読めた内容は以降のフェーズで「デフォルト案」として使う。

- プロフィールの内容は確定事項ではなく、あくまで提案の材料として扱う。「前回と同じく〇〇で良いですか？」と必ず確認を取る
- 「確度：高」の項目はまとめて一度に確認して良い（例：「技術スタックはいつも通り Next.js + Tailwind、デザインはシンプル寄りで進めて良いですか？」）
- Vault が見つからない、またはプロフィールが未作成の場合は、そのまま Phase 1 に進む

### Phase 1: 要求の理解・代替案の確認・目的とゴール

依頼はたいてい「〜を作りたい」という手段の形で届く。いきなりゴールの質問を並べず、まず自由に話してもらい、その中から「解決したいこと（課題）」と「作りたいもの（手段）」を分けて理解する。課題が分かれば、作らずに済む方法も検討でき、本当のニーズを深掘りできる。

**1. 自由に話してもらう**

最初は決まった質問ではなく、次のような趣旨で自由に話してもらう（言い回しは状況に合わせて変えて良い）。

> 作りたいもの・やりたいことを教えてください。資料やページのリンク、画像、スクリーンショットなどがあると、より正確に理解できます。どのページや機能に関わるかがはっきりしなくても、こちらで理解に努めるので、イメージできている範囲で大丈夫です。

- 受け取った資料・リンク・画像は実際に読む。読めなかったもの（ログインが要るページなど）は推測で埋めず、読めなかったことを伝えて、内容を教えてもらう
- 追加実装では、話に出た画面・機能に当たる既存のコードと `docs/spec.md` の項目を探し、どこの話かを特定してから次へ進む

**2. 課題と手段に分けて言い直し、確認する**

説明が大まかなとき、まとまっていないとき、手段だけが語られているときは、次の形で言い直して確認する。

> ありがとうございます。やりたいこととしては「〜を解決したい」のですね？ そのために「〜を作りたい」という理解でよろしいでしょうか？

- 課題が読み取れないときは、推測した課題を2〜3個の選択肢にして聞いて良い
- 説明が十分に具体的で、課題と手段がはっきりしているときも、一行で言い直して認識を合わせる
- ずれていたら、直された内容でもう一度言い直す。合意が取れるまで次へ進まない

**3. 代替案を確認する（必要なとき）**

課題に対して、次のような「作らずに済むかもしれない方法」がありそうなら投げかける。

- 同じ課題を解決する既存のサービス・ツール
- 今あるツールの使い方の工夫や運用で解決する方法
- 追加実装では、プロダクトの既存機能の使い方で解決する方法（最初に確かめる）

進め方：
- 思いつきで出さず、Web 検索や既存コードの確認で裏を取ってから、2〜3件に絞って出す
- 作ることを否定する言い方にしない。代替案ごとに「できること」と「足りなそうなこと」を添えて並べ、そのうえで開発が必要な理由を聞く
  例：「A なら〜はできますが、〜はできません。B は〜で代わりになりますが、手間が残ります。それでも作りたい理由は、この差にありますか？」
- 開発する理由が「代替案の〇〇が足りない」なら、その〇〇は外せない要件として Phase 3 で必ず扱う
- 「作ること自体が目的（学びたい、自分好みにしたい）」も正当な理由として受け取り、それ以上は掘らない
- 代替案で十分と分かったら、仕様設計はそこで終えて良い。代替案の使い方の説明に切り替える
- 有力な代替案が見当たらないときは、この手順を省いて良い（省いたことを一言伝える）

検討した代替案と開発する理由は、`GOAL` の項目（新規なら GOAL-5、追加実装なら今回の追加の目的の項目）に記録する。

**4. 目的とゴール**

ここまでで分かったことを踏まえて、まだ分からない点だけを聞く。

- 新規：このプロダクトで達成したいゴール（例：仕事の受注、採用、作品発表、自己ブランディング）、想定する利用者と最終的にしてほしい行動、どう使われる想定か（URLを名刺代わりに渡す、SNSから流入、検索から流入 など）
- 追加実装：`references/additional-development.md` の Phase 1 を参照する

回答が短くても、読み取れる意図を言語化して「つまり〇〇ということですね？」と確認する。

### Phase 2: チェックリストの骨組みを作る

ゴールが見えたら、`references/checklist-templates.md` から該当するプロダクト種別のテンプレートを読み、項目（カテゴリ）とサブ項目を組み立てる。

- テンプレートはそのまま使わず、Phase 1 のゴールに合わせて項目を足し引きする
- プロフィールで「よく対象外にする項目」とされているものは、最初から `[-]` 候補として提示する（理由を添えて、ユーザーに確認する）
- 骨組みができたらユーザーに提示し、「この分け方で進めて良いか」「足りない項目はないか」を確認する
- 追加実装（B・C）の場合は、既存部分は対象外とし、追加する機能に関する項目を中心に組む。組み方と ID の振り方、既存の項目への影響の洗い出しは `references/additional-development.md` の Phase 2 に従う

この時点ではほぼすべてが `[ ]` で構わない。全体像を先に見せることが目的。

### Phase 3: 項目ごとのヒアリング・提案・完了条件

項目を一つずつ（関連が強いものはまとめて）深掘りする。

**質問の仕方**
- 一度に聞くのは1〜3問まで。可能なら AskUserQuestion ツールで選択肢を出し、「その他」も許す
- 回答を受け取ったら、次の質問に進む前に必ず「ユーザーからの質問・割り込みへの対応」（本ファイル末尾）の確認を行う
- どの項目について聞いているかをIDで示す（例：「TOP-3 のファーストビューについてです」）
- 回答が短くても、読み取れる意図を言語化して確認する
- 「おまかせ」と言われたら、推奨案とその理由を示して確認を取る

**推測と提案**

ただ質問を並べるのではなく、ゴールから逆算して、ユーザーが言及していない要素を提案する。

- 「目的が〇〇なら、△△もあった方が良いと思いますがどうでしょう？」という形にする
- 提案ごとに「なぜ必要か」を一言添える
- 採用されたら該当項目に追加し、不要と言われたら `[-]` にして理由を記録する

**完了条件**

項目が確定に近づいたら、完了条件の案を出して確認してから `[x]` にする。

### Phase 4: 未言及項目の拾い上げ

ヒアリングが一段落したタイミング（各項目の深掘りが終わったとき、ユーザーが「だいたいこんな感じ」と言ったとき、デザインフェーズに入る前）に、`docs/spec.md` を見直して `※未言及` と `[~]` の項目を洗い出す。

- 未言及の項目は「XXXXについては、ご意見どうですか？」と自然に投げかける
- ユーザーが意識していなさそうな項目は、デフォルト案を添えて聞くと答えやすい
  例：「特にこだわりがなければ、画像の遅延読み込みと Lighthouse 90点以上を目安にしようと思いますが、それで良いですか？」
- `[~]` の項目は、迷っていた点を思い出させて決めてもらう
- 一度に全部聞かず、優先度の高い順に2〜3項目ずつ聞く

「全体デザイン」「パフォーマンス」「SEO」「アクセシビリティ」「運用・更新」などの横断的な項目は特に未言及になりやすいので意識して拾う。

### Phase 5: デザイン案

Phase 0 の判定に応じて進め方を変える。デザインに関するフィードバックも、チェックリストの項目IDに紐づけて記録する（例：「PROF-3 の経歴表示は B案の年表形式で確定」）。

**A：完全新規 → Claude Design で作成**
- 確定した項目をもとに、Claude Design 用のデザインブリーフを `docs/design-brief.md` に作成する
  - 目的・ゴール、想定ユーザー、ページ構成、各ページの掲載情報（チェックリストのIDを残す）
  - 方向性の異なる3案のコンセプトとそれぞれの狙い
  - トーン、配色やフォントの希望、参考サイト（プロフィールのデザインの好みも反映する）
- ユーザーにブリーフを Claude Design で使ってもらうよう案内し、作成されたデザインのリンクを共有してもらう。リンクは `docs/design.md` に記録する
- デザインを見たユーザーの感想を、項目単位でフィードバックとして取る
- 修正点は Claude Design への修正依頼文としてまとめて渡す

**B：追加実装（Claude Design あり）→ 既存デザインへの追記**
- `docs/design.md` の既存デザインを前提とし、新しい方向性はゼロから作らない
- 既存の配色・タイポグラフィ・コンポーネントに合わせた追加画面／追加セクションの要件をまとめる
- 「既存デザインのどこに、何を追記するか」を明記した追記依頼文を作り、ユーザーに Claude Design の該当デザインへ追記してもらう
- 既存デザインとの整合性で迷う点は選択肢を示して確認する

**C：追加実装（Claude Design なし）→ 既存コードと画面を踏まえて提案**
- 既存のコードを読み、CSS フレームワーク／UIライブラリ、デザイントークン、共通コンポーネント、類似画面のレイアウトパターンを把握してから提案する
- 可能なら開発サーバーを起動して既存画面を確認する（スクリーンショットがあればユーザーに共有してもらう）
- 既存コンポーネントを再利用する前提で、追加画面の案を2〜3パターン提示する。各案で「再利用する既存コンポーネント」と「新規に作るもの」を明記する
- 必要に応じて既存スタイルを流用したモックアップを `mockups/` に作る

### Phase 6: シナリオ・ウォークスルー

項目単位では見えない「項目同士のつながりの抜け」を見つけるため、具体的な利用シナリオに沿って仕様を通しで確認する。

1. シナリオを2〜3本作り、ユーザーに確認してもらう
   - 基本シナリオ：最も典型的な使われ方（例：「朝開く → 作業ごとに記録 → 夕方日報を出力」）
   - 例外シナリオ：うまくいかないとき（例：「記録を忘れて後から追加」「日付をまたぐ作業」「入力途中でタブを閉じる」）
   - 長期シナリオ：時間がたったとき（例：「半年後に過去ログを探す」「データが1万件になる」）
   Phase 1 で聞いた実際の使われ方をもとに、ユーザー自身の言葉に近い形で書く
2. 各シナリオを一歩ずつ進め、各ステップで「どの項目IDの仕様で実現されるか」を対応付ける
3. 対応する項目がない、項目同士が食い違う、完了条件では判断できないステップを「詰まりポイント」として挙げる
4. 詰まりポイントをユーザーに提示し、新しい項目として追加するか、既存項目を修正するかを決める

ウォークスルーの結果は `docs/spec.md` の「シナリオ」セクションに記録する。

```markdown
### シナリオ2：記録を忘れて後から追加する
1. 15時に、昼の作業を記録し忘れていたことに気づく → INPUT-1
2. 13時の作業として追加したい → ⚠ 時刻を指定して追加する仕様がない → INPUT-5 として追加（検討中）
3. 日報に正しい順番で出る → EXPORT-2（時刻順で出力）
```

一度に全シナリオを見せず、1本ずつ進めてユーザーと一緒に確認する。

追加実装の場合は、新しいシナリオに加えて、既存のシナリオのうち今回の追加で流れが変わるものも通しで見直す（`references/additional-development.md` の Phase 6）。

### Phase 7: 仕様レビュー

会話の流れに引っ張られた見落としを防ぐため、`spec-reviewer` サブエージェントに `docs/spec.md` をレビューさせる。

- サブエージェントには会話の経緯を渡さず、`docs/spec.md` と（あれば）`docs/design.md` だけを読ませる。仕様書だけで意図が伝わるかの確認も兼ねる
- 返ってきた指摘は、そのまま仕様に反映しない。重要度の高い順に、項目IDを添えてユーザーに質問の形で提示する
  例：「レビューで、INPUT-1 は一行入力なのに EXPORT-3 では作業内容の詳細説明を前提にしている、という食い違いが指摘されました。日報には一行のログをそのまま並べる形で良いですか？」
- ユーザーが「問題ない」と判断した指摘は、理由を決定ログに残す
- 追加実装の場合は、「追加開発の記録」での今回の No（追加1 など）と、追加・変更した項目IDを伝え、追加分と既存の項目との食い違いを重点的に見てもらう（会話の経緯は渡さない）
- `spec-reviewer` が使えない環境では、Claude 自身が同じ観点（`spec-reviewer` の定義を参照）で見直しを行う

### Phase 8: 仕様確定とプロフィール更新

**仕様確定**
- `[ ]` と `[~]` が残っていないか確認する
- 残っている場合は、決めるか、`[-]` 対象外にするか、「実装しながら決める」として保留事項に明示するかをユーザーに選んでもらう
- `[x]` の項目すべてに完了条件があるか確認する
- `docs/spec.md` 全体を最終確認してもらい、合意後に実装へ進む
- 追加実装の場合は、`references/additional-development.md` の Phase 8 に従って実装へ引き継ぐ

## ユーザーからの指摘への対応

ユーザーが「XXXのXXXが気になる」と言ったら：
1. 該当する項目IDを特定して「PROF-3 の経歴の見せ方についてですね」と確認する
2. 確定済み `[x]` の項目でも遠慮なく `[~]` に戻して再検討する。完了条件も合わせて見直す
3. その変更が他の項目やシナリオに影響する場合は、影響する項目IDも挙げて確認する

## ユーザーからの質問・割り込みへの対応

ヒアリングは Claude が一方的に質問を進めるものではなく、会話のキャッチボールである。ユーザーからの質問や疑問は、Claude の質問への回答よりも優先して扱う。ユーザーが質問したのに無視されると、「聞いても答えてもらえない」と感じてヒアリング全体への信頼が下がり、本当に気になっていることを言わなくなってしまう。

### 毎回の回答で確認すること

AskUserQuestion の回答や、チャットへの入力を受け取るたびに、次の質問へ進む前に以下を確認する。

1. 「その他」の自由記述欄に、回答ではなく質問・疑問・相談が書かれていないか
   - 例：「AとBの違いがよく分からない」「おすすめはどれ？」「そもそもこの機能いる？」
2. 選択肢を選ばずに、チャット欄から直接メッセージが送られていないか
   - フォームを閉じて送られたメッセージは、ほぼ確実に質問か割り込みである
3. 回答の中に、別の項目についての意見や懸念が混ざっていないか
   - 例：「Aでいいけど、そういえばスマホでも使えるの？」

疑問形（「？」「〜かな」「〜って何」）だけで判断せず、「回答として成立しているか」で判断する。回答として成立していない自由記述は、すべて質問や相談として扱う。

### 質問や割り込みがあったときの進め方

1. **予定していた次の質問をいったん止める**。同じターンで新しい AskUserQuestion を出さない
2. **ユーザーの質問に、通常の文章で先に答える**。選択肢の違いを聞かれたら、それぞれのメリット・デメリットと、Phase 1 のゴールに照らしたおすすめを示す
3. 質問への回答で、元の質問に答えられる状態になったか確認してから、**元の質問を聞き直す**（「では改めて、INPUT-2 についてはどちらにしますか？」）
4. 質問が別の項目に関するものなら、その項目IDを特定し、`docs/spec.md` に `[~]` として記録したうえで、「いったん今の INPUT-2 を決めてから、ENV-1 のスマホ対応について詳しく話しましょうか？それとも先にスマホの話をしますか？」と順番をユーザーに選んでもらう
5. 質問が仕様そのものへの疑問（「この機能いる？」）なら、その項目のゴールとの関係を説明し、必要なら `[-]` 対象外にするかを確認する

### 複数の質問をまとめて出しているとき

AskUserQuestion で複数の質問を出し、そのうち一部の回答に質問が含まれていた場合：

- 普通に答えられた質問は確定・検討中として記録する
- 質問が含まれていたものは未回答として扱い、上記の手順で先に答えてから聞き直す
- どれを記録し、どれを聞き直すのかをユーザーに明示する
  （「INPUT-1 は都度入力で確定しました。INPUT-2 はご質問に先にお答えします」）

### 割り込みが多いとき

同じ種類の質問（選択肢の意味が分からない、など）が続く場合は、質問の出し方を見直す。選択肢に一言説明を添える、専門用語を避ける、一度に出す質問数を減らす、などで調整し、その傾向は Phase 8 でプロフィールの「ヒアリングの好み」に記録する候補にする。
