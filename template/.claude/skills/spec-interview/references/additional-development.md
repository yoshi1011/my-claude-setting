# 追加開発モード

既存のプロダクトに機能を足すとき（Phase 0 の判定が B・C）に読む。SKILL.md の各フェーズの進め方はそのまま使い、このファイルの指示を上乗せする。

追加開発で一番起きやすい失敗は、新しい機能の仕様だけを固めて、既存の仕様や仕組みとの食い違いに実装の途中で気づくこと。そのため、既存の仕様書・コード・外部との取り決め（API など）への影響を、ヒアリングの早い段階から洗い出す。

## 規模の見立て

Phase 1 で要求が分かったら、規模を見立ててユーザーに確認する。小さな追加で全フェーズを通すと、会話が重くなるだけで得るものが少ない。

| 規模 | 目安 | 進め方 |
|---|---|---|
| 小 | 既存の画面や項目への少しの変更。データ構造も外部との取り決めも変わらない | Phase 1 → 影響の洗い出し → Phase 3 → Phase 8。デザイン・シナリオ・レビューは省いて良い |
| 中・大 | 新しい画面、データ構造の変更、外部との取り決めの変更のどれかがある | 全フェーズを通す |

省くフェーズはユーザーに伝え、同意を取る。迷ったら「中・大」として扱う。

## 仕様書への追記の仕方

既存の `docs/spec.md` は新しく作り直さず、追記する。

**今回の追加の節**

冒頭の「前提」の後に「追加開発の記録」の節がなければ作り、今回の追加を1行で書く。中身は各カテゴリの項目に書き、ここには一覧だけを置く。

```markdown
## 追加開発の記録
| No | 日付 | 内容 | 種別 | 状態 | 追加・変更した項目 |
|---|---|---|---|---|---|
| 追加1 | 2026-10-30 | 導入を検討しているパッケージの情報収集 | B | ヒアリング中 | PROJ-8〜10（追加）、PROJ-3・PROJ-4（変更） |
```

- 種別は今回の判定（B・C）。冒頭の「前提」の種別は最初の開発のときの記録なので書き換えない
- 状態は「ヒアリング中」「確定」「実装済み」のどれか

**項目の置き場所と ID**

- 既存のカテゴリに属する項目は、そのカテゴリの末尾に、続きの番号で追加する（例：`PROJ-7` まであれば `PROJ-8`）。番号を詰め直したり、振り直したりしない。既存の ID は他の文書やコードのコメントから参照されている
- 既存のどのカテゴリにも属さない機能なら、新しいカテゴリを作る（既存のカテゴリの後ろ、「シナリオ」の前に置く）
- 追加した項目には `（追加1）` のように、どの追加で決まったかを付ける
- 目的の項目：今回の追加の目的、検討した代替案、開発する理由は、今回の追加で最初に足す項目に書く（既存のカテゴリなら続きの番号の項目、新しいカテゴリなら `-1`）

**既存の項目を変えるとき**

- 確定済み `[x]` の項目を変えるときは `[~]` に戻し、変更の内容と理由を併記する。合意が取れたら `[x]` に戻し、完了条件も見直す
- 変更前の内容は消さず、決定ログに「何を・なぜ変えたか」を残す
- 冒頭に「状態：確定」などの記述があれば、ヒアリング中は「追加1をヒアリング中」のように書き換え、確定したら戻す
- 進捗サマリの数は、追加・変更のたびに更新する

## Phase 1：追加の目的

SKILL.md の Phase 1 の 1〜3（自由に話してもらう → 課題と手段の言い直し → 代替案）は同じように行う。代替案では、**プロダクトの既存機能の使い方で解決できないか** を最初に確かめる。既存機能で済むなら、それが一番安く確実。

そのうえで、プロダクト全体のゴールは聞き直さない（既存の `GOAL` を読めば分かる）。代わりに次を聞く。

- なぜこの追加が要るか（今、何に困っているか）
- 既存の `GOAL` のどれに効くか。どれにも当てはまらなければ、ゴール自体が変わっていないかを確認する
- 追加したあと、何がどうなっていれば成功か

## Phase 2：骨組みと影響の洗い出し

`references/checklist-templates.md` の「既存プロダクトへの機能追加」のテンプレートに加え、既存の `docs/spec.md` のカテゴリと横断項目（データ・運用・セキュリティなど）から、追加分に関わるものを拾って骨組みを作る。テンプレートのカテゴリ ID（`SCOPE`・`UI` など）が既存の仕様書の ID と重なるときは、既存のカテゴリに合流させるか、別の ID にする。

骨組みと同時に、既存の仕様と仕組みへの影響を洗い出す。

1. **既存の仕様書**：追加によって前提が変わる確定済みの項目。ID を挙げ、それぞれ何が変わりそうかを書く
2. **既存のコード**：変わりそうなモデル・画面・処理。特に、追加分と同じデータを扱う処理（上書き・削除・集計など）は、追加分のデータを壊さないかを確かめる
3. **外部との取り決め**：API の仕様書、外部のエージェントやジョブへの指示書、エクスポートの形式など、アプリの外にいる相手が前提にしているもの。変えるなら、古い形式で来たときの扱い（互換性）を決める
4. **既存のデータ**：データ構造が変わるなら、既にあるデータをどう移すか。初期値をどうするか
5. **既存のシナリオ**：今回の追加で流れが変わるシナリオ

洗い出した結果は、骨組みと一緒にユーザーに見せる。影響のある既存の項目は `[~]` に戻してから Phase 3 で扱う。影響が見当たらない観点は「影響なし」と明記する（見ていないのと区別するため）。

## Phase 5：デザイン

SKILL.md の B・C に従う。画面の追加・変更がなければ、Phase 5 は省いて良い（ユーザーに伝える）。

## Phase 6：シナリオ

- 新しいシナリオは、今回の追加の基本シナリオと例外シナリオを作る
- 既存のシナリオのうち、Phase 2 で「流れが変わる」としたものを、追加後の仕様で一歩ずつ進め直す。変わったステップには `（追加1で変更）` と付ける
- 既存のシナリオを書き換えたときは、変更前の流れが分かるように、決定ログに要点を残す

## Phase 8：実装への引き継ぎ

- 「追加開発の記録」の状態を「確定」にする
- `PROGRESS.md` があれば、今回の追加のタスクを、既存のタスクの後ろにフェーズとして追加する（なければ作る）
- 実装用のブランチ名を提案する（プロジェクトやユーザーの決まりに合わせる）
- 実装が終わったら、「追加開発の記録」の状態を「実装済み」にする
