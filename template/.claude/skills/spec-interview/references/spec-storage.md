# 仕様書の記録先（Document / md）

仕様書は、Claude の Artifact の **Document（Claude Docs）** か、md ファイル（`docs/spec.md`）のどちらかに記録する。Phase 0 で記録先を決め、以降はずっとそこに書く。

SKILL.md などで `docs/spec.md` と書いてあるところは、記録先が Document のときは **仕様書用の Document（今回のタブ）** と読み替える。

## 1. 記録先を決める（Phase 0）

ユーザーには聞かず、まず Claude が既存の記録を探す。

**既存の記録の探し方**（リポジトリありのとき）

- md：`docs/spec.md` があるか
- Document：`README.md` と、その他開発ルールをまとめた資料等（例：`CLAUDE.md`、`CONTRIBUTING.md`、`docs/` 配下）に、**仕様書用** の Document の URL が記録されているか。見つかった URL は Claude Docs のツールで読み、Document であること（タブの一覧が返ること）を確かめる
- 要求用の Document（request-interview の記録先）は仕様書の記録先として使わない。要求ドキュメントと仕様書は別々の Document にする

**判定**

| 状況 | 記録先 |
|---|---|
| 仕様書用の Document の記録がある | その Document の tabs（Document の中のタブの一覧）に、今回のヒアリングの新しいタブを足す |
| `docs/spec.md` がある | `docs/spec.md` に追記する（今までどおり） |
| 両方ある | どちらに記録するかユーザーに聞く |
| どちらもない（このリポジトリで初めての仕様ヒアリング） | ユーザーに選んでもらう（下記） |

**どちらもないとき**

AskUserQuestion で聞く。

> 仕様書をどの形で残しますか？

- 「Claude の Document に残す（推奨）」：説明は「チームで共有・コメント・直接編集ができ、ヒアリングごとにタブを分けて残せます」
- 「md ファイル（`docs/spec.md`）に残す」：説明は「リポジトリの中でコードと一緒に管理できます」

Document を選んだら、新しい Document を作る（「2. Document に記録する」）。そのあと、次を AskUserQuestion で聞く（リポジトリありのときだけ）。

> 今回作成する Document を、今後も追記する資料として README に記載しますか？

- 「記載する」：`README.md` に「3. README に書く内容」を追記する。`README.md` がなければ、作ってよいかを確認してから作る
- 「記載しない」：README は変えない。「次回以降も同じ Document に追記したいときは、Document の URL を伝えてください」と伝える

リポジトリがないとき（Claude のアプリのチャットなど）も、Document か md かは同じように聞く。README の質問はしない。Claude Docs のツールがない環境では聞かずに md にし、そのことを伝える。

## 2. Document に記録する

Document の操作（作成・タブの追加・書き込み・読み返し）は Claude Docs のツールで行う。最初の操作の前に Claude Docs の guide（`topic.index`。タブを足すときは `topic.tabs` も）を読み、その書き方に従う。

**新しく作るとき**

- Document の名前は `<リポジトリ名・プロダクト名> 仕様書`
- 最初のタブは `YYYY-MM-DD <テーマ>`。中身は `assets/spec-template.md` の構成にする
- 作ったら Document を開いて見せる

**既存の仕様書用 Document に追記するとき（2回目以降）**

- 今回のヒアリング用に新しいタブ `YYYY-MM-DD 追加N <内容>` を作る（N は既存のタブの続きの番号）。今回決めることは、このタブに書く
- 新しいタブの中身は `references/additional-development.md` の「仕様書への追記の仕方」に合わせる。冒頭に今回の前提（種別・Claude Design・元になった要求ドキュメント）、続けて追加した項目、既存の項目の変更、シナリオ、決定ログを置く
- 項目 ID は **タブをまたいで通し番号** にする。始める前にすべてのタブを読み、既存のカテゴリ ID と最後の番号を確かめる
- 既存の項目を変えるときは、新しいタブに「変更：<ID>（元のタブ名）／変更前／変更後／理由」を書く。元のタブの項目は書き換えず、`（追加N で変更）` とだけ書き添える
- 過去のタブは、上の書き添え以外は書き換えない。ヒアリングごとの記録として残す
- 「追加開発の記録」の一覧の表は作らない。タブの一覧がその代わりになる
- 進捗サマリ（確定・検討中などの数）は、今回のタブの冒頭に、今回の分だけを書く

**書き方の決まり**

- チェックリストの書式（`[x]` `[~]` `[ ]` `[-]` と項目 ID・完了条件）は md と同じにする
- 合意が取れたら、その場で今回のタブを更新する（md のときと同じ）
- ユーザーやチームが Document を直接直したときは、その直しを優先し、Claude が上書きしない

## 3. README に書く内容

「記載する」を選ばれたら、`README.md` に次の節を追記する（既に同じ節があれば、URL だけを直す）。

```markdown
## 仕様書の記録先

- 仕様書（spec-interview）：[<Document の名前>](<Document の URL>)
- 記録のルール
  - 仕様ヒアリング（spec-interview）の結果は、この Document に記録する。`docs/spec.md` は作らない
  - 最初の仕様は最初のタブに、2回目以降はヒアリングごとに新しいタブ（`YYYY-MM-DD 追加N <内容>`）を作って記録する
  - 項目 ID はタブをまたいで通し番号にする。既存の項目を変えたときは、新しいタブに変更の内容を書き、元のタブの項目には「（追加N で変更）」とだけ書き添える
  - 要求ドキュメント（request-interview）は、この Document とは別の Document に記録する
  - Document は画面上部の Share からチームに共有する
```

追記したら `git diff` で確かめ、コミットするかをユーザーに確認する。

## 4. サブエージェントに仕様書を渡すとき

`spec-reviewer`・`requirement-checker` などのサブエージェントは、ファイルしか読めず、Document を直接読めない。記録先が Document のときは、呼び出す側が次のようにしてから渡す。

1. Claude Docs のツールで、渡すタブ（初回のタブと、今回に関係する追加のタブ）を読む
2. 内容をそのまま md にして、一時ファイル（スクラッチのディレクトリなど、リポジトリの外）に書き出す。タブごとに `## タブ：<タブ名>` の見出しで区切る
3. そのパスを、サブエージェントの「受け取る情報」の「仕様書のパス」として渡す。書き出した md は読むためだけのもので、仕様の正本は Document であることも添える

## 5. Document の共有

Document は、作った直後は作った本人しか開けない。Claude からは共有できないので、作ったら「画面上部の Share から、チームの人を追加してください」とユーザーに伝える。
