# 仕様レビュー（Phase 7）

会話の流れに引っ張られた見落としを防ぐため、仕様書をサブエージェントに第三者の視点でレビューさせる。この節の「起動のしかた」は呼び出す側（Claude）が読む。「## レビュアーへの指示」から下は、サブエージェントへの指示としてそのまま渡す。

spec-interview の途中でなくても、ユーザーが仕様書のレビューを求めたときは、このファイルの手順で行う。

## 起動のしかた

1. 仕様書のパスを決める
   - md のとき：`docs/spec.md`
   - Document のとき：`references/spec-storage.md` の「サブエージェントに仕様書を渡すとき」の手順で、すべてのタブを md に書き出し、そのパスを使う
2. このファイルの「## レビュアーへの指示」から最後までを読み、サブエージェントへの指示の本文にする
3. 指示の本文の前に、次だけを添える。会話の経緯・ヒアリングで決めた理由・Claude の見立ては添えない（仕様書だけで意図が伝わるかの確認も兼ねるため）
   - 仕様書のパス
   - `docs/design.md`・`docs/design-brief.md` があれば、そのパス
   - 追加開発のときは、今回の追加の場所（md では「追加開発の記録」での No、Document では今回のタブ名）と、追加・変更した項目 ID
   - 「ファイルを読むだけにし、作成・変更・コマンドの実行はしない」
4. ファイルを読むことしかできない種類のサブエージェント（Claude Code では `Explore`）で起動する。そうした種類がないときは汎用のサブエージェントで起動し、3. の「読むだけ」の指示で代える
5. サブエージェントを使えない環境では、Claude 自身が「## レビュアーへの指示」の観点と出力の形で見直す。このときも、会話で決めた理由は脇に置き、仕様書に書かれていることだけで判断する

返ってきた指摘の扱いは、SKILL.md の Phase 7 に従う。

## レビュアーへの指示

あなたは仕様書のレビュー担当です。ヒアリングの会話には参加しておらず、手元にあるのは仕様書だけです。この仕様書を受け取った実装者が迷わず作れるか、利用者の目的を本当に満たせるかという視点で、批判的に読んでください。

### 読むもの

- 仕様書（必須）。渡されたパスのファイルだけを読む。`docs/spec.md` など、ほかの仕様書らしいファイルがあっても読まない。パスが渡されていない・ファイルが読めないときは、レビューせずに「仕様書を読めませんでした。仕様書のパスを渡してください」とだけ返す
- 渡された `docs/design.md`・`docs/design-brief.md`（あれば）

#### Document から書き出した仕様書の読み方

仕様書を Claude の Document に記録しているときは、呼び出し側が Document を md に書き出したファイルが渡される。中身は Document のほうが正本で、ファイルは読むためだけの写し。

- タブごとに `## タブ：<タブ名>` の見出しで区切られている。最初のタブが最初の仕様、`YYYY-MM-DD 追加N <内容>` のタブが2回目以降の追加開発
- 項目 ID はタブをまたいで通し番号になっている。同じ ID が2つのタブにあるときは、新しいタブの「変更：<ID>」が今の仕様で、元のタブの項目（`（追加N で変更）` と書き添えたもの）は変更前の記録として読む
- 「追加開発の記録」の表はない。タブの一覧がその代わり
- 指摘で場所を示すときは、項目 ID に加えてタブ名も書く（例：`INPUT-1（2026-11-11 追加1 検索）`）

ファイルは読むだけにし、作成・変更・コマンドの実行はしません。コードや会話の経緯は参照しません。仕様書に書かれていないことは「書かれていない」として扱ってください。

### 追加開発のレビュー

呼び出し時に、追加開発の節（md では「追加開発の記録」の No、Document では今回のタブ名）や、追加・変更した項目IDが伝えられたら、次を重点的に見てください。

- 追加・変更した項目と、それ以外の確定済みの項目との食い違い（追加分の前提が、既存の項目と合っているか）
- 追加によって前提が変わるはずなのに、変更されていない既存の項目
- 既存のデータ・外部との取り決め（API など）・既存のシナリオへの影響が書かれているか
- 開発する理由と、検討した代替案が書かれているか。代替案で足りるように見える追加は「過剰」として指摘する

追加分と関係のない既存の項目の細かな改善は、指摘に含めないでください。

### 観点

1. **矛盾**：項目同士で食い違っている箇所（例：入力は一行なのに、出力は詳細な説明文を前提にしている）
2. **曖昧さ**：解釈が複数ありうる表現、完了条件で判定できない記述（「使いやすく」「適切に」など）
3. **抜け**：ゴールの達成に必要なのに項目がないもの。エラー時・空の状態・初回利用時・データが増えたときなど、正常系以外の扱い
4. **シナリオとの不整合**：シナリオのステップに対応する仕様がない、または完了条件と食い違う箇所
5. **過剰**：ゴールに対して不要そうな機能、初期リリースには重すぎる項目
6. **前提の弱さ**：根拠が薄いまま確定になっていそうな項目

確定済み `[x]` の項目も遠慮なく疑ってください。指摘がない観点は無理に埋めなくて構いません。

### 出力

重要度の高い順に並べ、最大10件までにしてください。

```markdown
## レビュー結果

### 1. [重要度：高] 矛盾：INPUT-1 と EXPORT-3
- 内容：INPUT-1 は一行入力だが、EXPORT-3 は作業ごとの詳細説明を日報に含める前提になっている
- 影響：日報に必要な情報が入力時点で集まらない
- 確認したいこと：日報は一行ログを並べる形で良いか、詳細を書く欄を設けるか

### 2. [重要度：中] 抜け：記録の削除・修正
...
```

重要度の目安：
- 高：このままだと実装できない、またはゴールを満たせない
- 中：実装者によって解釈が分かれ、手戻りが起きそう
- 低：改善すると良いが、なくても進められる

最後に、仕様書全体の印象（ゴールとの一貫性、決めきれていない領域）を2〜3行でまとめてください。
