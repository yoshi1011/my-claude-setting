# 要求ドキュメントからの引き継ぎ

request-interview スキルで作られた要求ドキュメントを受け取って仕様設計を始めるときに読む。SKILL.md の各フェーズの進め方はそのまま使い、このファイルの指示を上乗せする。

要求ドキュメントは、依頼者（ユーザーサポート・PO など非エンジニア）が「依頼者にしか答えられないこと」だけを答えたもの。困りごと・現場の事実・成功の状態・優先度はそろっているので、同じことを聞き直さない。一方で、画面の動きやエラー時の扱いなどは意図して決めていない（「10. エンジニアに任せること」）。

## 要求ドキュメントの形

要求ドキュメントには2つの形がある。中身のセクション（1〜11）は同じなので、以降の手順はどちらでも同じに扱う。

| | Claude の Document（今の形） | md ファイル（以前の形・Claude Docs が使えない環境） |
|---|---|---|
| 置き場所 | Claude Docs の Document。1依頼 = 1タブ（`YYYY-MM-DD <短い名前>`） | `docs/requests/YYYY-MM-DD-<短い名前>.md` など |
| 見分け方 | 冒頭の「概要」の表の「種類」が「要求ドキュメント（request-interview）」 | frontmatter に `type: request`、または冒頭の「概要」の表の「種類」が同上 |
| 状態 | 「概要」の表の「状態」：ヒアリング中 / 合意済み | `status: draft` / `ready`（または「概要」の表の「状態」） |
| 対象・関係する画面 | 「概要」の表の「対象」「関係する画面」 | `target`・`related_screens` |
| 画面デザイン | 「概要」の表の「画面デザイン」 | `design_url`（ない場合はセクション6の「画面ラフ」） |
| 読み方 | Claude Docs のツールで読む（Document を読んでタブの一覧を出し、該当タブの本文を読む）。Web 取得では読まない | ファイルを読む |

以降、「合意済み」は `ready`、「ヒアリング中」は `draft` と同じ意味として読む。

## 見つけ方

Phase 0 で、次のどれかに当たるときにこのモードに入る。

- ユーザーが要求ドキュメントの URL（`claude.ai/artifact/...`）やパスを示したとき。URL は Claude Docs のツールで読み、Document でなければ（Design など）要求ドキュメントとしては扱わない
- リポジトリの開発ルールをまとめた資料等に要求用の Document の URL が記録されていて、その中に「合意済み」で、まだ仕様に取り込んでいないタブがあるとき
- `docs/requests/` に `status: ready` で、まだ仕様に取り込んでいない md があるとき

候補が複数あれば、どれを扱うかユーザーに聞く。Document が読めない（共有されていない）ときは、依頼者に Share からの共有を頼むようユーザーに伝える。

「ヒアリング中」（`draft`）のものは、依頼者がまだ読み返していない。取り込む前に、依頼者に確認済みかをユーザーに聞く。

## フェーズごとの扱い

| spec-interview | 要求ドキュメントがあるとき |
|---|---|
| Phase 0 状況の判定 | 「対象」「関係する画面」から新規か追加実装かを判定する。「5. 今の動き」が「依頼者の認識（未検証）」なら、**ここでコードと突き合わせ**、食い違いをユーザーに伝える |
| Phase 1 要求の理解・代替案・ゴール | **省略**。セクション1〜4を一行に要約して「この理解で進めます」と確認するだけにする。代替案はセクション5で既存機能の確認が済んでいれば省く |
| Phase 2 骨組み | セクション6（アイデア）と7（優先度）を初期値にして組む。「いらない」は最初から `[-]` 候補（理由は要求ドキュメントから写す）。セクション11の確認事項を、骨組みと一緒に依頼者向けの文面にして渡す（後述） |
| Phase 3 ヒアリング | セクション10（エンジニアに任せる）の項目が中心になる。「絶対ほしい」は必ず項目にする。セクション6のアイデアは提案材料として扱い、そのまま確定にしない |
| Phase 5 デザイン | 画面デザインの URL（「概要」の表、またはセクション6）があれば、それを出発点にする。既存の画面の再現と、依頼者の案・Claude の追加案が並んでいる（どれも変更可）。開けないときは依頼者に共有を頼む |
| Phase 4・6〜8 | 通常どおり。Phase 6 のシナリオは、セクション3の実例をもとに作る |

## 事前確認が残っているとき

セクション9に「要確認」が残っていれば、Phase 0 の最初にユーザーへ一覧で伝える。

> 要求ドキュメントに、まだ確認が済んでいない項目が1件あります：「利用規約の変更が要るか（確認先：法務）」。このまま仕様設計を進めて良いですか？ 確認の結果次第で仕様が変わる可能性があります。

進めるかどうかはユーザー（エンジニア）が決める。進める場合、関係する項目は `[~]` にして「事前確認待ち」と併記する。

## 依頼者にしか答えられない疑問が出たとき

仕様を詰める途中で、業務のルールやお客様の事情など、依頼者にしか答えられない疑問が出たら、**推測で埋めない**。

- `docs/spec.md` の該当項目を `[~]` にし、「依頼者への確認事項」として併記する
- 依頼者にそのまま送れる形（専門用語なし・選択肢つき）にしてユーザーに渡す
- **セクション11（依頼者への確認が必要になりそうな点）は、Phase 2 の骨組みと一緒に送る**。依頼者の答えを待つあいだに Phase 3 を進められるようにするため。答えがないと決められない項目（実現の方法を左右するものなど）は、送った時点で項目IDを添えてユーザーに伝え、Phase 3 では後回しにする
- 途中で出た疑問は、それを待たないと進めない項目があればその場で送り、そうでなければ区切りのよいところでまとめて送る

## 要求が変わったとき

依頼者の答えで要求そのものが変わることがある（例：「数分で読める」が、実現が難しいと分かって「10〜20分なら待てる」に緩んだ）。

- 変わったと気づいたら、変わったことにしてすぐ進めず、まず依頼者に確認する。前の要求と今の答えを並べて「要求ドキュメントでは『〇〇』でしたが、今のお答えは『△△』です。どちらが今のご希望に近いですか？」と聞く（依頼者に直接聞けないときは、この文面をユーザーに渡す）。前の要求のままなら、変更として扱わない
- 要求ドキュメントは書き換えない（Document のタブも md も）。依頼者が合意した時点の記録として残す
- `docs/spec.md` の該当項目に、変わった後の要求と「要求の変更（依頼者の回答）」を併記し、決定ログに変更前と変更後、きっかけを残す
- 変わったのが「絶対ほしい」（セクション7）や「成功の状態」（セクション4）なら、`GOAL` の項目（追加実装なら今回の追加の目的の項目）の「出典：要求ドキュメント」の内容も直し、「（〇〇は依頼者の回答で変更）」と添える
- 変更があったことは、Phase 8 で仕様を確定するときにユーザーへ一覧で伝える。依頼者に結果を共有するかはユーザーが決める

## 仕様書への記録

- `docs/spec.md` の冒頭の「前提」（追加実装なら今回の追加の節）に、元になった要求ドキュメントの場所を書く。Document なら URL とタブ名、md ならパス
- `GOAL` の項目（追加実装なら今回の追加の目的の項目）には、要求ドキュメントのセクション1・4の内容を写し、「出典：要求ドキュメント」と添える
- 要求の段階で聞くべきだった確認漏れが見つかったら、request-interview の `references/precheck.md` への追記をユーザーに提案する
