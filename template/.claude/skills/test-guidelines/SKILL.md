# テスト記述ガイドライン

## 基本方針

- テストは「仕様（期待される振る舞い）」を確かめるために書く。実装の内部構造を写し取るためには書かない
- カバレッジ目標は 90%。ただし数値のためだけのテストは書かない
- テストの説明文（`it` / `test` / `describe` などの文字列）は日本語で、「どんな状況で、何がどうなるか」が分かるように書く
  - 良い例: `未ログインの場合、ログイン画面へ遷移する`
  - 悪い例: `test1` / `正しく動く`

## 構成

- 1 テストにつき確かめることは 1 つ（1 つの振る舞い）に絞る
- Arrange（準備）/ Act（実行）/ Assert（検証）の順に、境界が読み取れるように書く
- テスト間で状態を共有しない。実行順に依存させない
- 共通の準備処理はヘルパー / ファクトリにまとめ、テスト本文には「このテストで何が違うのか」だけを残す

## 網羅すべきケース

- 正常系だけでなく、異常系・境界値・権限（認可）のケースを含める
- 日時を扱う処理はタイムゾーン・日付境界・月末 / 閏年を意識する。現在時刻は固定する
- 画面のテストでは、ローディング・エラー・空状態の表示も確かめる

## モック・スタブ

- モックするのは外部境界（HTTP・DB・時刻・乱数・外部サービス）に限る。テスト対象そのものや、その内部の協調オブジェクトを過度にモックしない
- モックの呼び出しだけを検証して終わるテストにしない。可能な限り観測可能な結果（戻り値・状態・表示）を検証する

## 避けるべきテスト（レビューで指摘する）

- **常に通るテスト**: 検証（assert / expect）がない、検証対象がモックが返した値そのもの、例外が握りつぶされている、非同期処理の完了を待たずに終わる など
- **結果がわかりきったテスト**: 言語・フレームワークの標準機能やライブラリの動作を確かめているだけのもの、定数をそのまま比較しているだけのもの
- **実装の写し**: 実装と同じ計算をテスト内で再実装して比較しているもの
- **テストのためのテスト**: テストを通すためだけにプロダクトコードへ分岐や公開メソッドを追加しているもの
- **壊れやすいテスト**: 実行環境のタイムゾーン・ロケール・実行順・待ち時間（sleep）に依存するもの
- **E2E での過剰検証**: 単体テストで確かめられる細部を E2E で重複して検証しているもの

## フロントエンド

- 処理内容が多い関数（変換・計算・バリデーション等）は単体テストを書く
- コンポーネントのテストは、ユーザーから見える振る舞い（表示・操作結果）で検証する
- e2e の仕組みがある場合は、主要な操作フローの e2e テストも書く
