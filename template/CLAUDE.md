## 仕様設計（spec-interview）

- 「〜を作りたい」「〜を追加したい」など要件が曖昧な依頼、新規プロダクトの立ち上げ、既存プロダクトへの機能追加の相談では、すぐ実装せず `spec-interview` スキルに従ってヒアリングから始める（`/spec <テーマ>` でも開始できる）
- 仕様は仕様書（`docs/spec.md` または仕様書用の Document）に項目ID付きのチェックリストで記録し、確定項目には完了条件を付ける。既に仕様書がある場合は作り直さず追記する（Document なら新しいタブを作る）。どちらもない初回は、Document（推奨）か md かを指示者に確認する
- 仕様書が Document のとき、サブエージェント（仕様レビュー・requirement-checker など）には、Document を md に書き出した一時ファイルのパスを渡す（Document を直接読めないため）
- 仕様が合意されるまでテスト・実装に進まない。確定後は仕様書の項目IDと完了条件を、要求・テストケースの根拠として使う
- 仕様のレビューは、spec-interview の仕様レビューの手順（`spec-interview` スキルの `references/spec-review.md`）でサブエージェントに行わせる
- `request-interview` で作られた要求ドキュメント（Claude の Document、または依頼者から受け取った md ファイル）があれば、それを元に仕様を詰める（spec-interview の一部の手順を省ける）
- 要件が明確な依頼（不具合修正、範囲がはっきりした小さな変更など）では省略してよい

## 開発ルール全般

- フレームワークが用意している自動生成コマンドを活用してベースを出力してから編集すること
- コメントは原則不要です。自明なコメントは書かない。
  - Classやメソッドの説明コメントはなるべく記述すること。ただし、なにをするためのClass、メソッドなのかの説明に留めること。作成した経緯などの説明は一切不要
- 実装にはテストを書く。テストの説明文は日本語。カバレッジ目標90%。
  - e2eの仕組みがある場合、フロントエンドのe2eテストも書いて実施すること。

## 進捗管理（PROGRESS.md）

- 作業開始時（新しいセッション・ブランチ切り替え後を含む）に PROGRESS.md を読み、該当 Phase の状態・残作業を確認してから着手する
- 次のタイミングで必ず PROGRESS.md を更新する: 仕様が確定したとき / 実装の各 Step が完了したとき / コミット・PR を作成する前 / 作業を中断・終了するとき
- 新しい Phase・作業を始めるときは、冒頭「全体マイルストーン」表に行を追加し、本文に Phase の節を作る。状態欄は実態に合わせて随時更新する
- Phase の節に書く内容: 仕様書のパス / 指示者の決定事項 / Step ごとのチェックリスト（[x] 完了 / [ ] 未着手）/ テスト結果（件数）/ チェック・レビューの実施状況 / ブランチ・PR・主なコミット / 残作業・今後のタスク候補
- 途中で作業が止まっても、PROGRESS.md だけで再開地点が分かる状態を保つ

## frontend / backend / infra 開発の詳細指針

詳細な設計指針はスキルに切り出している。該当する場面ではエージェントが自動で参照する。

- **frontend（`frontend/` 配下）を編集する場合** → `frontend-design` スキルを参照
- **backend（`backend/` 配下）を編集する場合** → `backend-architecture` スキルを参照
- **infra（`infra/` 配下、Terraform を実行する CI のワークフロー）を編集する場合** → `infra-architecture` スキルを参照
  - `terraform apply` / `destroy` とクラウドへの変更操作は行わない。apply は指示者が行う
  - レビュー・チェックの指摘を受けてインフラを変更する場合は、費用に影響することが多いため、変更する前に必ず指示者の了承を得る

## `.claude` ディレクトリの置き場所

- `.claude` ディレクトリ（エージェント定義・スキル・設定・エージェントのメモ）はリポジトリ直下にだけ置く。`backend/.claude/` など配下には作らない
- サブエージェントは作業ディレクトリをリポジトリ直下にしてから起動する。配下に作られていたら、リポジトリ直下の `.claude/` に統合して削除する

## チェッカー・レビュアーへの依頼と結果の扱い

orchestrator で作業しているときも、通常のセッションで作業しているときも、次に従う。

- 起動する前に `.claude/agents/<名前>.md` の「受け取る情報」の表を読み、そこに書かれた情報だけを渡す。実装の説明・意図・「ここを見てほしい」といった要約は渡さない（実装者の説明に引きずられずに確認してもらうため）
- 結果に「ユーザーに確認したい点」がある場合は、自分で判断して進めず、その内容を指示者に質問して回答を得てから次へ進む
- 結果に「規約への追記の提案」がある場合は、作業の報告と一緒に指示者に示し、了承されたものだけを該当するスキルに反映する

## レビューエージェントの起動 (必須)

コード変更が一段落するたびに、該当する reviewer agent を必ず proactively 起動する。
- backend 変更 → `backend-reviewer`
- frontend 変更 → `frontend-reviewer`
- infra 変更 → `terraform-infra-reviewer`
- 複数が変更されたなら該当するものを並列起動
- どの変更でも、レビュアーと同じタイミングで `failure-pattern-checker`（起こりうるエラー・失敗のパターンの検証）と `security-checker`（起こりうるセキュリティの問題の検証）も並列起動する

`.claude/settings.json` の `permissions.deny` に `Agent(<名前>)` が書かれているレビュアーは OFF になっているため起動しない（設計指針スキルを書き終えたら deny から消して ON にする）。飛ばした場合は、そのことを作業の報告に書く。

起動するタイミング:
- コードの変更が一段落してテストが all pass した直後（frontend は E2E を流した直後も）
- ユーザーへの作業完了報告（「Step N 完了」「実装完了」など）を出す直前
- 「次のステップに進む？」「コミットする？」「apply しますか？」と提案する直前
- マルチステップ作業中は各ステップの完了ごと（まとめて1回ではない）
- PR / commit を作成する直前

**テスト / E2E / terraform validate / plan が pass したことはレビュー完了の代わりにならない**。動作確認とは独立に必ず起動する。

呼ばないケース:
- ドキュメント（*.md / 仕様書）のみの変更
- typo・コメントのみの修正
- 一時的なデバッグ出力の追加・削除
- コード生成ツールの生成物のみが更新された場合
- 同セッション内で同じ差分を既にレビュー済みの場合
